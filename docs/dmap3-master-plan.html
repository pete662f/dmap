Deadlines and hard constraints

Deadline

DAWA shuts down 17 August 2026 — three weeks from today

Danmarks Adressers Web API (api.dataforsyningen.dk) closes 17 August 2026, postponed once already from 1 July 2026. It is being replaced by Datafordeleren, where the address data (DAR) is reached by file download or GraphQL, behind API keys or OAuth. BBR data on DAWA already stopped updating in December 2023.

Consequence for dmap3: do not write a single line against DAWA. Go straight to Datafordeleren DAR bulk file download, imported into our own index. This is actually the better architecture anyway — we want a local address index, not a remote API call on every keystroke. Register a Datafordeleren user this week so the credential process is not on the critical path.

Scope

Android and iOS are both product requirements — decided 2026-07-28

rev. 1 and rev. 2 of this plan were Android-only, and the superseded rebuild-plan.html listed "iOS or a shared KMP core in the first two milestones" as an explicit non-goal. That is no longer the case: the app ships on both platforms. This is a scope decision, not a technical one, and it changes the plan in three places — the architecture gets a shared core (see Platform strategy), every phase exit criterion now reads "on both platforms", and the schedule grows.

Consequence: doing this from P0 is much cheaper than retrofitting it after P3, so the foundations phase splits in two. But Apple enrolment, signing and macOS CI do not go in week 1 — week 1 belongs to Datafordeleren, which has an immovable external deadline. Apple has lead time; it does not have a cliff.

Method

No dmap2 code is reused — only what dmap2 taught

dmap3 is a rebuild from the ground up, not a migration. The dmap2 Android app and its backend have been deleted from the repository; nothing is ported, nothing is copied, and no file is carried across. The reason is not that the old code was bad — much of it worked — but that reuse smuggles unexamined decisions forward, and the whole point of a second attempt is that each decision gets made deliberately with the benefit of having made it once already.

Where the knowledge lives: docs/dmap2-lessons.md — the three expensive mistakes, what worked and should be repeated, and the hard-won operational details (glyph builds, index storage, proxy behaviour, tuning knobs) that were embodied in the deleted scripts. Read the relevant section before building each corresponding piece. The old code remains readable at the dmap2-final tag as a reference, never as a source to copy from.

Rejseplanen has a real cost cliff

Free tier is 50,000 API requests per month, non-commercial only. Above that, or if you sell data or sell a service using the data, it is commercial: €5,000/year for 100k requests/day, €8,500/year for 200k/day. Data is licensed CC BY 4.0 — attribution required.

Design consequence: architect to stay under 50k/month by default. Use the free GTFS static feed locally for everything that does not need live data (stop search, stop rendering, line geometry, timetable browsing) and spend API calls only on live journey planning and live departures. That is a 10–50× reduction in call volume versus naive use. Note the cliff triggers on volume alone — more than 50k/month is itself commercial use, revenue or not, so success alone triggers it. The over-budget behaviour is a designed mode, not an outage (see Public transport).

MapLibre Compose is not production-ready yet

The official first-party maplibre-compose supports camera, layers, expressions, GeoJSON sources, feature querying, offline regions and Material 3 controls — but its own documentation states the feature set is incomplete, there may be bugs, and API stability is not guaranteed. Ferrostar moved its Android UI onto it in 0.50/0.51.

Design consequence: put every map interaction behind our own MapController interface, declared in the shared core and implemented natively on each platform. Back it with MapLibre Native + AndroidView on Android and MapLibre Native iOS via SPM on iOS (both safe, proven), and let the navigation screen use Ferrostar's own UI layer. If MapLibre Compose stabilises we swap the Android implementation without touching feature code — and iOS never depended on it in the first place.

New in rev. 3

Ferrostar's iOS side is weaker than its Android side

Ferrostar (0.53.0 at time of writing) describes itself as a solid alpha: the iOS UI is "usable, with some rough edges", the project is explicitly not yet ready for production, and there are no API stability guarantees. The Rust core is the mature part; the SwiftUI layer is the thin part. rev. 2 already said to treat the navigation state machine as "a dependency we could replace rather than a foundation we cannot" — with iOS committed, that stops being a hedge and becomes a requirement.

Design consequence: the dual-platform navigation trial is promoted from a spike to a gate (P2.5) that runs before any navigation UI is written. If Ferrostar's SwiftUI layer does not hold up on a real Danish route, the fallbacks are: vendor a pinned fork and patch it, drive the Rust core directly through UniFFI and build our own SwiftUI nav screen, or contribute upstream. All three are survivable. Discovering them mid-P3 is not.

Apple adds release gates Android does not have

A navigation app needs UIBackgroundModes: location, and App Review scrutinises background location hard. We have a good story — turn-by-turn guidance is the canonical justification — but it has to be told, with a demo account or a demonstrable route, and a privacy manifest declaring exactly what the location data is used for.

Design consequence: P7 grows. Budget for two store submissions, an Apple privacy manifest, background-location justification, and at least one rejection-and-resubmit cycle. Also: CocoaPods entered maintenance mode in August 2025 with no releases after Q2 2026, so SPM is the only sensible distribution path for both our own framework and our dependencies.

Legal

Speed-camera warnings are legal in Denmark

Unlike Germany and France, Denmark has no prohibition on apps that warn about speed controls — community traffic-alert apps are legal to use. What is illegal is active radar/laser detector hardware, and flashing your headlights to warn other drivers. So a speed-camera and fotovogn layer is fine to build; a hardware detector integration is not.

The place model — one ID to rule them

This is the spine of the product. dmap2's single most expensive mistake was that a tapped POI, a search result and a saved place were three unrelated things. In dmap3 they are one type with one ID, and every feature — search, tap, save, share, route, navigate — speaks that ID. 

PlaceId  = "<namespace>:<native-id>"      stable, never regenerated, safe to persist
             osm:n1234567      OSM node / way / relation
             ovt:08f2ab…       Overture GERS ID
             cvr:1018234567    CVR P-enhed (production unit)
             dar:0a3f50…       Datafordeleren address UUID
             rjp:008600626     Rejseplanen stop ID
             usr:9f2c…         user-created POI (ours)

Place {
  id, name, altNames[]          da / en, plus synonyms for search
  category                      our own normalised taxonomy, not OSM tags
  lat, lon, geometry?           point always; polygon when we have one
  address { road, houseNo, postcode, city }
  contact { phone, web, email, socials }
  openingHours?, brand?
  sources[] { namespace, nativeId, licence, fetchedAt }   provenance, always
  confidence                    how sure are we this exists
  visibility                    public | private (user POIs)
}

The rule: a Place may have several entries in sources[] — an OSM node conflated with an Overture record and a CVR P-enhed is one Place with three sources. The canonical ID is chosen by priority (osm > ovt > cvr > usr), so an OSM-backed place keeps a stable ID even as enrichment sources come and go.

Conflation — the part that goes wrong

No shortcut exists here. Overture's places theme contains no OSM data — places come from Meta (~59M of ~75M rows), Microsoft, Foursquare and PinMeTo — and the GERS bridge files map places back to those sources only; OSM bridge files exist for buildings, divisions and transportation, not places. So OSM ↔ Overture is fuzzy matching, and it is the dominant conflation workload, not the fallback.

  1. OSM ↔ Overture: our own matcher — block on distance (~75 m) and category, score on normalised-name similarity, accept above a conservative threshold, queue the ambiguous band for review. A wrong merge is worse than a duplicate: unmatched pairs are just two pins until reviewed. Prototype on one municipality and measure precision/recall before designing P2 around it.
  2. CVR ↔ existing: match on normalised address (DAR address UUID) + name similarity above a threshold. A CVR P-enhed at the same address with a similar name is the same business.
  3. Unmatched CVR: keep as its own Place, geocoded from its DAR address, flagged confidence: address-derived so the UI can show it slightly differently.
  4. Never delete on re-import. Re-run conflation into a new table, diff against the live one, and apply the diff — so user edits and manual overrides survive every monthly Overture release.

User-created POIs — two-tier rendering

A user-added POI must appear on the map immediately, and a tile rebuild takes minutes. So POIs render from two places at once:

Tier 1 — baked into tiles

OSM + Overture + CVR POIs are baked into the vector tiles by Planetiler with osm_type, osm_id, place_id and our normalised category. Rebuilt weekly. Zero runtime cost, perfect label placement, works offline.

Tier 2 — live overlay

User POIs and anything created since the last tile build come from a GeoJSON bbox endpoint (/places/bbox?…&since=…) rendered as a MapLibre GeoJSON source with the same icon and label styling. On the next tile build they graduate into Tier 1 and drop out of the overlay. since is the tile-build watermark published by the tile server, not client wall-clock — otherwise a place renders twice in the window between creation and rebuild.

The client cannot tell the difference: both tiers produce features carrying a place_id, and the tap handler is the same code path for both. This is what replaces dmap2's 548-line hit detector — tap, read place_id, call PlaceDetail.byId. Done.

Editing model

  • Create, edit, moderate own POIs; every change is an append-only revision, never an in-place update.
  • Private POIs (visibility: private) never enter the shared index or tiles.
  • An "improve this place" flow on OSM-sourced places writes a local override rather than editing the OSM record — and optionally queues an OSM note for upstream contribution.
  • Overrides are applied after conflation, so an upstream re-import can never silently clobber them.

Speed cameras and hazards

Legal in Denmark (see constraints). There are two very different classes of hazard, and conflating them produces a bad product:

TypeSourceVolumeBehaviour
Fixed ATK (stærekasser) OSM highway=speed_camera, enforcement relations; cross-check against Vejdirektoratet ATK maps ~20 today, planned expansion to 60 Static. Bake into tiles. Warn on approach with direction awareness — the enforcement relation carries which direction it measures.
Section control enforcement=average_speed relations (from/to nodes) Few Zone, not a point. Show entry, average speed across the zone, and exit.
Mobile fotovogne Crowdsourced — ours. No open dataset exists. Unbounded, ephemeral Time-decaying reports: confirm/deny voting, expire after a few hours, weight by reporter reliability.
Other hazards Vejdirektoratet traffic messages + crowdsourced Moderate Roadworks, accidents, closures. Same time-decay model as fotovogne.

Design the hazard layer as its own service from day one

Hazards are not places. They have geometry plus a direction, a validity window, a confidence and a decay function. Give them their own table, their own endpoint (/hazards/bbox, /hazards/along-route) and their own contract. The along-route query is the one that matters for navigation: given the active route polyline, return hazards within a corridor ahead, ordered by distance along the route. Do this server-side — the client should never scan a bbox during navigation.

Warning UX: announce once at a distance scaled by speed (roughly 10–15 seconds of travel time, not a fixed metre count), show the enforced limit next to the current speed, and never repeat within the same approach.

Routing: Valhalla for car, bike and foot

Valhalla is the choice because its costing is evaluated per request against the tiles, not baked into a precomputed hierarchy. Car, bike and foot come from one container and one tile set, and a user preference ("avoid motorways", "prefer cycle paths", "avoid stairs") is a JSON field, not a rebuild. OSRM's contraction hierarchies make it faster per query but require a full graph rebuild to change a profile — which is disqualifying when you ship three modes plus user preferences.

Car — auto

  • Motorway/toll/ferry avoidance as user prefs
  • Live traffic later via Vejdirektoratet messages as edge penalties
  • Hazard-aware: not a costing input, a display layer

Bike — bicycle

  • bicycle_type: city / cross / road / mountain
  • use_roads and use_hills sliders map directly to Danish cycling culture
  • Elevation tiles optional — Denmark is flat enough to defer

Foot — pedestrian

  • Walking speed, step/stair penalties
  • Accessibility variant: avoid steps, prefer kerb ramps
  • Used for the first/last leg of transit journeys

Build cost — sanity check

A full-planet Valhalla build is documented at roughly 600 GB of temporary disk and ~15 hours (without elevation). The Denmark extract is on the order of 450 MB against a ~80 GB planet PBF, so a Denmark build should land in the minutes-to-tens-of-minutes range with a few GB of working space. Estimate by extrapolation — measure it in P1 and record the real number. Keep valhalla_build_tiles thread count configurable; OOM during tile building is the common failure mode and lowering threads is the documented fix.

Do not use Valhalla for public transport

Valhalla can ingest GTFS and build transit tiles, but transit tiles are only valid for 60 days after generation and the multimodal path has open correctness issues. That is a recurring maintenance burden for a worse answer than the national journey planner. Use Rejseplanen instead and let Valhalla do what it is excellent at: the street network.

Multimodal door-to-door

A real journey is walk → transit → walk, sometimes bike → transit → walk. Rejseplanen plans the transit portion between stops; Valhalla plans the legs at each end. Compose them in our own Routing service: 

1. Valhalla pedestrian  origin → candidate departure stops   (local, free, fast)
2. Rejseplanen trip     departure stop → arrival stop        (1 API call, live)
3. Valhalla pedestrian  arrival stop → destination           (local, free, fast)
4. stitch into one Route with typed legs: Walk | Transit | Bike | Drive

Rejseplanen's trip endpoint also accepts coordinates directly, which is simpler but gives up control of the walking legs. Use coordinates for the first implementation, then switch to stop-to-stop with our own walking legs when we want Danish-quality pedestrian routing at each end. Cache aggressively — identical A→B within a few minutes should not spend a second call.

Decide the over-budget behaviour now, not at request 50,001

When the monthly meter runs out, the transit-gateway degrades, never fails: journey planning and departure boards fall back to GTFS static schedule times, clearly labelled "scheduled" instead of "live". The client contract carries realtime: bool on every transit answer from day one so the UI can badge it — retrofitting that flag later touches every screen.

Also check before P5: whether Rejseplanen Labs offers GTFS-RT under the same free terms as the static feed. A feed-level realtime source would let the gateway poll once centrally and serve every user from cache — that restructures the entire cost problem and could make the 50k budget nearly irrelevant.

Location precision — the jerky-puck fix

Root cause, stated plainly. GPS delivers about 1 fix per second. The display renders at 60–120 Hz. If you move the puck when a fix arrives, you get exactly one jump per second — that is the hopping. On top of that, raw fixes wander several metres laterally even on a straight road, and GPS-derived bearing is unusable below walking pace. These are three separate problems and they need three separate fixes. Most implementations fix one and wonder why it still looks wrong.

The pipeline

           ├──────────────── shared/commonMain ────────────────┤
raw fix ─▶ L1 gate ─▶ L2 filter ─▶ L3 snap ─▶ L4 predict ─▶ L5 bearing ─▶ L6 camera ─▶ screen
  ▲        reject      Kalman     to route     per-frame    smoothed     frame-synced
  │        garbage     smooth     polyline     dead-reckon  course       puck + map
native L0                                                       native L6
Fused / CoreLocation                              Choreographer / CADisplayLink

This is the part that pays for the shared core. L1 through L5 are pure functions over a stream of fixes — no platform API, no UI, no I/O. They live in commonMain, are written once, tuned once, and regression-tested once against the same recorded Danish traces from both the Kotlin and the iOS test targets. Only the two ends are native: L0, which asks the OS for fixes, and L6, which drives the camera on the platform's frame clock.

rev. 2 described this pipeline as "about 400 lines of well-tested Kotlin, not a platform problem". With two platforms committed that sentence gets stronger, not weaker: it is 400 lines that would otherwise be written and tuned twice, in two languages, against two sets of bugs.

L0

Ingest — get the best fixes each OS will give you native

Android

  • PRIORITY_HIGH_ACCURACY with intervalMillis = 1000 and minUpdateIntervalMillis = 500. Google explicitly sanctions second-scale intervals for foreground mapping apps; it is background use that must not do this.
  • Foreground service with location type for the whole navigation session — otherwise the OS throttles you and the jitter gets worse, not better.
  • Never set setMaxUpdateDelayMillis during navigation — batching is the enemy here. Use it only in browse mode to save battery.

iOS

  • CLLocationManager with desiredAccuracy = kCLLocationAccuracyBestForNavigation and activityType = .automotiveNavigation — the activity type is what tells the OS this is a vehicle and changes its filtering behaviour.
  • allowsBackgroundLocationUpdates = true plus the location background mode, and pausesLocationUpdatesAutomatically = false — the default pause behaviour will silently stop your navigation session.
  • Request When In Use first and escalate; do not open with an Always prompt.

Both: keep the raw fix stream and hand it to the shared pipeline as a platform-neutral RawFix (lat, lon, accuracy, speed, bearing, monotonic timestamp). Every layer below is testable only if you can replay raw traces — and only if the trace format does not know which OS recorded it.

L1

Gate — throw away bad fixes before they poison the filter

  • Reject accuracy > 50 m outright while driving.
  • Reject any fix implying an impossible jump (> ~60 m/s from the last accepted position).
  • Order by elapsedRealtimeNanos, not wall clock, and drop out-of-order arrivals.
  • Track consecutive rejections — three in a row means "signal lost", which L4 handles differently.
L2

Filter — a constant-velocity Kalman filter

Feed position and the reported accuracy (as measurement variance) into a simple constant-velocity Kalman filter. Output is a smoothed position and a velocity estimate — the velocity is what L4 needs. This is the standard, literature-backed fix for Fused Location and Core Location jitter alike. Roughly 80 lines of pure Kotlin in commonMain, fully unit-testable against recorded traces, no dependencies. Run it in a locally projected plane (metres — a tangent plane at the last fix is fine), never on raw lat/lon: filtering degrees is the classic implementation bug.

Note: the filter alone will not make it look smooth. It removes noise, not the 1 Hz stepping. People who stop here are the ones who conclude "GPS is just jumpy".

L3

Snap to route — the single biggest visual win

While a route is active, project the filtered position onto the active route polyline within a corridor (~25 m). This eliminates all lateral wander instantly: the car is on the road because it is mathematically constrained to the road. Ferrostar's Rust core does exactly this — line snapping plus a navigation state machine for step advance and deviation detection — so this is a library call, not a project.

  • Outside the corridor for N consecutive fixes → off-route → trigger reroute. Do not snap harder.
  • When not navigating (free browse/drive), use Valhalla Meili trace_attributes periodically to snap to the road network, or accept the filtered position. Snapping without a route is genuinely harder — do not over-engineer it.
L4

Predict — a per-frame ticker is what makes it look like a car

This is the layer almost everyone omits. Run an animation loop on the frame clock (withFrameNanos/Choreographer on Android, CADisplayLink on iOS). On each frame, advance the puck along the snapped polyline by velocity × Δt. When a new fix arrives, do not teleport — ease the predicted position toward the corrected one over 250–400 ms.

Split: the frame source is native, the advance-and-ease math is shared. Each shell ticks its own display link and calls one shared advance(elapsedNanos): PuckState. That keeps the interesting 60 lines in one place and leaves each platform to do only what it alone can do.

Now the puck moves every frame at 60–120 Hz instead of once per second, follows the road's curvature because it advances along the polyline, and corrections are invisible because they are eased rather than applied.

Tunnels and signal loss: keep dead-reckoning along the route at last known speed, surface a subtle "estimated position" state, and ease back gently when fixes return. Never freeze the puck — a frozen puck reads as a crashed app.

L5

Bearing — interpolate the course, not just the position

Position is nearly atomic; course is what needs interpolating. Rules that produce a stable heading:

  • While snapped: take the bearing from the route tangent at the puck's position. The heading then turns exactly as the road turns — through curves, roundabouts and slip roads — with zero GPS noise. This is the trick that makes it feel premium.
  • Free driving above ~3 m/s: use GPS bearing, smoothed with a shortest-arc angular low-pass so it never takes the long way round 0°/360°.
  • Below ~3 m/s: hold the last bearing. Never use raw GPS bearing at low speed and never let the puck spin while stationary at a light.
  • The device compass is unreliable inside a car (magnetic interference) — use it for pedestrian mode only.
L6

Camera — drive it from the same frame tick native

The classic bug is the puck and the camera animating on different clocks, so the puck slides around the screen during turns. Fix: compute puck position, puck bearing and camera target in one frame callback, then set both. This is per-platform code — the same rule, written twice, because it talks directly to MapLibre's camera API on each side.

  • Puck anchored at a fixed screen point (~⅔ down), not centred — you want to see what is ahead.
  • Course-up: map bearing = smoothed course, so the map rotates and "turn left" points left. North-up is a user preference, not the default, in drive mode.
  • Pitch 45–60° in drive mode, 0° in browse mode, eased on transition.
  • Zoom as a function of speed — roughly z17 in town, easing to z15.5 at motorway speed — so the look-ahead distance stays constant in seconds, not metres.
  • Ease zoom out slightly on maneuver approach so the turn and its exit are both visible.

Speed display

  • Show speed from the Kalman velocity estimate, not Location.getSpeed() — the raw value flickers by several km/h at constant speed.
  • Speed limit while navigating from the route's edge attributes (Valhalla returns per-edge speed_limit via trace_attributes on the route shape, fetched once at planning time) — that pins the limit to the edge under the puck with no rendered-tile query. Tile maxspeed is the fallback for free driving. Danish OSM coverage is 100% on motorway/trunk/primary, 99.85% secondary, 77.16% tertiary — good enough to ship.
  • Over-limit styling on the speed readout; hazard warnings show the enforced limit beside current speed.

How to actually verify this works

Record real drives, replay them in tests. Capture raw fix streams (with timestamps and accuracy) on real Danish roads: a motorway stretch, a roundabout-heavy suburban route, central Copenhagen with tall buildings, and a tunnel. Store them as fixtures. Every layer L1–L5 is then a pure function over a trace and can be unit-tested and regression-tested on the JVM with no device.

Ferrostar ships simulated location providers for exactly this. Build the trace harness in P1, before the navigation UI exists — it is the difference between tuning by feel on the motorway and tuning by test.

New in rev. 3 — the fixtures are the cross-platform contract. Store traces as plain JSON (fix stream in, expected PuckState sequence out) with no platform in the format. Assert them from the commonTest source set and from the iOS test target through the exported framework. A trace recorded on an Android phone must produce byte-identical pipeline output on iOS; if it does not, the shared core has leaked a platform assumption and you want to know on the day it happens. Record on both devices so the fixture set covers both GPS stacks.

Navigation UI and camera

That division is exactly what we want, and its own architecture (shared Rust core, UniFFI bindings, native UI per platform) is the same bet we are making one layer up.

Platform strategy — one core, two shells

The rule is simple and it is the whole strategy: share everything that is a rule, write natively everything that is a surface. Business logic, domain models, network contracts, persistence and the location math go in shared/. Anything that touches a screen, a sensor, a permission dialog or an OS lifecycle is written twice, on purpose.

What this buys

  • One place model, one PlaceId, one conflation-aware repository — the spine of the product cannot drift between platforms.
  • One location pipeline, tuned once against one set of traces.
  • One set of gateway contracts, so a backend change breaks both builds at compile time rather than one of them at runtime.
  • Existing dmap2 Kotlin — PlaceModels, the Photon parser pattern, service interfaces — is portable rather than discarded.

What it does not buy

Be honest about the ratio. Expect 55–65% shared non-UI code, not 60–75% of the app. For a navigation product the expensive work is exactly what stays native: map layer installation, frame-synced camera, background lifecycle, permissions, audio session, notifications. That is most of P3 and P4, and KMP does not touch it.

The backend is doing more sharing than the shared module is. Eight gateways already hold search, conflation, routing, transit, hazards and identity server-side — keep it that way. Every time logic could live in a gateway or in the client, put it in the gateway.

Two interop rules that keep the Swift side pleasant

  1. Do not export StateFlow into SwiftUI screens. Keep native view models on each platform (ViewModel / @Observable) and let them call shared use cases that return plain suspend results. Presentation stays native, the Swift API stays idiomatic, and no presentation concern leaks into commonMain.
  2. Keep the exported surface small and stable. Everything not deliberately part of the Swift API is internal. The XCFramework's public surface is a design artifact — review it like an API, because that is what it is.

Client architecture

The source-set layout is above. What follows are the cross-cutting rules — the ones that decide whether the two shells stay in step or quietly diverge over six months.

The MapController contract

One interface in shared/contracts/, two native implementations. It exposes semantic commands and an event stream, never a map object: 

interface MapController
  commands   setCamera(target, zoom, bearing, pitch, ease) · setLayerVisible(id, bool)
             setGeoJson(sourceId, payload) · setBaseLayer(style) · fitBounds(bbox)
  events     Flow<MapEvent>  Tap(placeId) · CameraIdle(bounds) · StyleLoaded · Error

  impl androidApp  MapLibreNativeController — AndroidView + MapLibre Android SDK
  impl iosApp      MapLibreNativeController — UIViewRepresentable + MapLibre iOS SDK

CameraDirector   browse / drive / transit behaviours — rules shared, application native
LayerRegistry    poi · hazards · route · transit · imagery · user-overlay
                  layer ids and ordering shared; installation native

The point of "semantic commands" is that MapEvent.Tap carries a PlaceId, not a screen coordinate or a rendered feature. Resolution happens in the tile schema, not in the client — which is what kills dmap2's 548-line hit detector, and what stops us writing it twice.

Four rules — three carried forward from the dmap2 review, one new

  1. Every backend is an interface with an Unavailable implementation, written before the backend exists, and declared in commonMain so both shells get the same seam. This is what made Photon a drop-in in dmap2 and it is what will make Rejseplanen, hazards and routing drop-ins here.
  2. Backend URLs are a runtime setting in a debug drawer, not a compile-time BuildConfig chain. dmap2 spent ~120 lines of Gradle, two scripts and a recurring support question on this. rev. 3 upgrades this from preference to requirement — see below.
  3. The client never infers what the data should state. Tap → read place_id → look it up. No geometry-based guessing, ever.
  4. A feature is not done until it is done on both platforms. Not "Android now, iOS in the catch-up sprint". The catch-up sprint never happens, and a half-ported app is how a shared core rots into an Android core with a Swift wrapper.

Why runtime backend config stops being optional

dmap2's android/app/build.gradle.kts resolves each backend URL through a four-level chain — .env → local.properties → Gradle property → default — and bakes the result into BuildConfig. rev. 2 already wanted that gone. rev. 3 makes it non-negotiable: none of that machinery has an Xcode equivalent, and reproducing it as a build-phase script would be a genuinely miserable second implementation of a thing we already decided was a mistake.

Consequence: backend configuration is shared state read from the shared module at runtime, with a settings screen on both shells. This lands in P0b, before there is anything to configure — it is cheap then and expensive once eight gateway URLs exist in two places.

The transit-gateway is the one that pays for itself: it holds the Rejseplanen API key server-side (never in the APK), serves GTFS static answers locally at zero API cost, and caches live responses so a hundred users looking at the same departure board cost one call. It is also where the 50k/month budget is enforced and measured.

Identity — the backend dmap2 never had, and three features silently need

Reporter-reliability weighting, confirm/deny voting, private POIs that sync, and moderation all assume the server can tell users apart. Full accounts are overkill and a GDPR liability; total anonymity invites spam. The middle path: an anonymous device identity — the app generates a keypair, the identity-gateway issues an opaque ID and tokens. That is enough for weighting, rate limits and shadow-bans while storing zero PII. Real accounts (email) arrive only if cross-device sync or sharing ever demands them, as an upgrade of the same identity, not a migration.

  5. Ferrostar on real devices — both of them — with a Valhalla Denmark route, before designing the nav UI around it. This is now the P2.5 gate, not a side quest. Pay particular attention to the SwiftUI layer, which is the weakest part of an otherwise strong SDK.
  6. Valhalla Denmark build time and disk — my figure is extrapolated from planet-scale numbers. Measure it.
  7. MapLibre Compose stability at the moment you start P3; the assessment here is from July 2026 and this is a fast-moving library.
  8. The Kotlin SPM export path on your actual toolchain, in P0b. Official XCFramework-plus-SPM generation is recent; confirm it works on the Kotlin version you pin before you build a phase plan on it, and know that the community Gradle plugins are the fallback.
  9. Room KMP on iOS with your schema — pin the stable 2.7.x line and confirm migrations behave on device. Room 3.0 is alpha; do not let a nice changelog pull you onto it mid-project.
  10. Apple Developer enrolment lead time — start it in P0a week as a background task, and find out early whether you are enrolling as an individual or an entity, because the verification paths differ substantially.

The three things that decide whether this becomes the best Danish map app. First, the place model in P0 — one ID, one type, provenance on every row. Get it wrong and every later feature pays interest, exactly as dmap2's tap-resolution code did. Second, the location pipeline in P3 — snapping plus a per-frame predictor plus route-tangent bearing. That combination is the entire difference between "a map that shows where you are" and "a navigation app you would actually use in a car", and it is about 400 lines of well-tested Kotlin in commonMain, not a platform problem. Third, the OSM ↔ Overture matcher in P2 — there is no bridge-file shortcut, and its precision decides whether enrichment reads as magic or as duplicate pins. Prototype it before you trust it.

rev. 3 adds a fourth, and it is a discipline rather than a component: keep the two shells in step. The architecture makes sharing possible; only the habit of finishing both sides of a feature makes it real. Every phase above ends with an exit criterion that says "on both platforms" for exactly that reason.
