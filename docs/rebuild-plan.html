Build plan

dmap3 — rebuilding from the ground up

A concrete plan for the next iteration: the target stack, the contracts, the repository shape, and a seven-phase build order. Every choice traces back to a finding in the dmap2 stack review.

Drafted 2026-07-27 · companion document: docs/stack-review.html

Goals and non-goals

Goals

  • A Denmark-first native Android map app that looks and feels like a consumer product, not a demo.
  • Fully self-hosted data path: tiles, style, glyphs, sprites, search, imagery. No third-party map key in the client.
  • Places are first-class objects with stable ids — tap, search, save, share and route all refer to the same thing.
  • One command to a working stack from a clean clone, with honest incremental rebuilds.
  • Routing and offline are designed for from day one, even if they ship later.
  • Every quality gate that does not need the dataset runs in CI on every push.

Explicit non-goals

  • Coverage outside Denmark at detail zooms. A low-zoom world backdrop is acceptable; a world dataset is not.
  • Multi-tenant / public production hosting. Target is one machine plus personal devices.
  • iOS or a shared KMP core in the first two milestones.
  • Turn-by-turn voice navigation. Route display yes; guidance is a separate product.
  • User accounts, sync, or any server-side user state.
  • Re-implementing a geocoder from scratch when an index build will do.

The organising principle. dmap2's expensive code all sat where the client had to infer what the data should have stated. dmap3 pushes identity, category and geometry into the tile build and the place index, so the app reads facts instead of guessing them.

The contracts — write these first

dmap2's best result was that its interfaces held. Define these on day one, each with a real implementation, an Unavailable implementation, and a fake for tests. Nothing in ui/ ever imports a service implementation.

ContractShapeBacked byPhase
TileSource styleUrl(), attribution(), bounds() TileServer GL / PMTilesP1
PlaceSearch search(query, bias, limit): List<Place>
reverse(lat, lon): Place?		 place-gateway (SQLite/FTS5); Photon fallbackP3
PlaceDetail byId(PlaceId): PlaceRecord? place-gateway, keyed on osm_type:osm_idP3
Imagery tileUrlTemplate(): String?, isConfigured() ortofoto-gatewayP4
Routing route(from, to, mode): Route Stub → ValhallaP0 / P6
LocationProvider Flow<LocationState>, permission: Flow<PermissionState> Fused / MapLibre engineP2
BackendSettings Flow<BackendConfig>, update(...) DataStore, defaults from BuildConfigP0

The one addition over dmap2: LocationProvider is a Flow, not a poll. That deletes the while (isActive) { delay(1_500) } loop and makes location state testable without a map.

Build order

P0

Skeleton, contracts and gates

Half a day. Nothing renders yet; everything that will judge the project exists.

  • Repo layout, Taskfile.yml, libs.versions.toml, DMAP_ARTIFACT_ROOT resolution.
  • All seven contracts as interfaces with Unavailable + fake implementations.
  • AppContainer manual DI; BackendSettings on DataStore with BuildConfig defaults.
  • CI workflow: unit tests, ktlint, detekt, Android Lint, node --test. Green on an empty app.
  • Debug settings screen with editable backend URLs. Build this before the map.

Exit: task check passes in CI; the app launches to a settings screen that can point at any host without a rebuild.

P1

Tiles, style and a map on screen

The data pipeline, ported and improved from dmap2's proven scripts.

  • Planetiler task with pinned image, threads/heap knobs, checksummed extract — port from bootstrap-denmark.sh.
  • Style pipeline: pinned OSM Liberty clone → self-host rewrite → apply style-overrides.json → prefetch glyph fontstacks. Port prepare-style-assets.sh, convert the patch to declarative.
  • Style schema check: every override targets an existing upstream layer id. Wire into CI.
  • Compose + MapLibre with MapController from the start — commands in, Flow<MapEvent> out.
  • Denmark camera defaults, bounds and zoom limits — port MapPresentationConfig values verbatim, they are tuned.

Exit: clean clone → task bootstrap && task up → app renders Denmark with correct labels and no public network calls.

P2

Location, permissions and persistence

Everything stateful, before any feature needs it.

  • LocationProvider as a Flow; permission requested from the locate control or a compact prompt — never on first launch. Port dmap2's UX decision, drop its polling.
  • Styled puck, locate-me control, centred-on-user derivation from camera position.
  • Room + DataStore in place: settings, recents, saved places schema. Empty features, real repositories.
  • Ambient tile cache configured at startup (port the 256 MB default).

Exit: permission flow works cold; location state is unit-testable with no map instance; a recents row survives process death.

P3

Places — the structural fix

Highest-value phase

The phase that pays back dmap2's two most expensive findings.

  • Custom Planetiler profile layer: emit osm_type, osm_id, a normalised dmap_category, and POI polygons into the main tileset. No second tile pipeline.
  • pipeline/places/: build places.db (SQLite + FTS5) from the same extract — name, alt names, category, coordinates, address parts, id.
  • services/place-gateway/: 0-dependency Node service exposing /search, /reverse, /place/{id}, /healthz. Modelled on the ortofoto gateway.
  • App: tap → queryRenderedFeatures on one POI layer → read id → PlaceDetail.byId. Target under 100 lines total.
  • Debounced search UI, Denmark-biased, typed DTOs via the serialization plugin.
  • Place detail as a real navigation destination, not a card wired into the map screen.

Exit: a POI tap, a search hit and a saved place all yield the identical PlaceId; no reverse-geocode call is needed to label a tapped POI; the hit detector plus its tests fit in ~250 lines total (dmap2: 1,338).

P4

Imagery and map modes

Port the best-behaved service in dmap2 with minimal change.

  • Port ortofoto-proxy near-verbatim as ortofoto-gateway: 0 deps, token file only, 503 when unconfigured, node --test.
  • Token-file path is the only supported path; the gateway refuses an inline token unless an explicit dev flag is set (F9).
  • Raster layer inserted below labels/POIs; layer toggle; failure degrades back to vector with a message.

Exit: imagery toggle works, labels and pins stay above imagery, and no token appears anywhere in .env or the APK.

P5

Product polish and the release path

Turn it from "it works" into something installable.

  • Saved places and recents surfaced in UI; share-a-place intent.
  • Release build: R8 enabled, signing config, real versionCode strategy, cleartext restricted to debug via a network security config.
  • PMTiles as the shipping tile artifact; TileServer stays the dev path.
  • Screenshot or Compose UI tests for the map screen — the one area dmap2 had zero coverage.

Exit: a signed release APK installs on a phone, points at a LAN backend via the settings screen, and contains no cleartext permission.

P6

Routing

The seam reserved since P0 finally gets a service.

  • Valhalla container, Denmark tiles built in the same task graph, routing compose profile.
  • Routing implementation behind the existing contract; route line, distance, ETA, alternatives.
  • No guidance, no voice — display only.

Exit: a route renders between two PlaceIds with distance and ETA, and disabling the routing profile degrades cleanly to the stub.

P7

Offline regions

Where the PMTiles decision pays off.

  • Region selection UI backed by the Room schema laid down in P2.
  • Region download, storage accounting, eviction controls.
  • Offline place search: ship a pruned places.db per region.

Exit: airplane mode over a downloaded region still renders, searches and shows place detail.

Decisions to make before P1

1. Place index — build our own, or keep Photon?

Own index: no JVM, tens of MB, full control of Danish ranking and of the PlaceId contract, but we write and tune the relevance ourselves. Photon: proven quality out of the box, but 885 MB, 3 GB RAM, and it drove three separate workarounds in dmap2.

Recommendation: build our own as the default and keep Photon behind a compose profile as the escape hatch. The PlaceSearch contract makes this a reversible decision — which is exactly the property dmap2 proved was worth having. Danish addresses also have an official open dataset worth evaluating as an enrichment source; check its current licence and terms before depending on it.

2. Custom Planetiler profile, or post-process the tiles?

A custom profile means writing Java against Planetiler's API and maintaining it across upgrades. A post-process pass means a second tool rewriting the MBTiles after the fact.

Recommendation: custom profile. dmap2 already demonstrated what "second pipeline" costs — an 81 MB parallel tileset and an invisible style layer. Keep one build producing one artifact.

3. Manual DI, or Hilt?

AppContainer was 31 lines and caused no problems in dmap2, but dmap3 adds repositories, a database, a controller and multiple screens.

Recommendation: stay manual through P3, reassess at P5. Manual DI keeps build times low and makes test wiring trivial; adopt Hilt only if the container genuinely exceeds ~150 lines.

4. How much of dmap2 gets copied verbatim?

Rewriting proven code is its own risk. The candidates for straight ports are the ortofoto gateway, the glyph prefetch, the Denmark camera constants, the Planetiler invocation and the compose hardening.

Recommendation: copy those five verbatim on day one and mark them as ported in commit messages. Rebuild only what the findings say is structurally wrong — that is roughly 40% of the codebase, not 100%.

Engineering baseline

CI, from commit one

  • Unit tests (JVM only — no emulator, no dataset).
  • ktlint + detekt + Android Lint, all failing the build.
  • Style override schema check against the pinned upstream style.
  • node --test for every gateway.
  • A weekly scheduled job that re-runs the style schema check against upstream HEAD, so renames surface as a notification rather than a broken bootstrap.

Testing strategy

  • Pure decision logic in domain/ — heavily unit tested, as dmap2 did well.
  • Repositories tested against in-memory Room + a fake gateway.
  • MapController tested through its command/event API with a stubbed map.
  • Compose UI tests for the map screen states: loading, ready, unavailable, selection, imagery.

Security defaults

  • Cleartext permitted only in the debug manifest, scoped to private ranges by network security config.
  • Secrets are file paths, never values, in .env; gateways refuse inline secrets without a dev flag.
  • Services bind to 127.0.0.1 unless LAN exposure is explicitly opted into.
  • Every container keeps dmap2's hardening flags; add them at service creation, not later.

Documentation

  • architecture.md, setup.md, contracts.md describe the current state only — no milestone narration (F10).
  • docs/decisions/ holds one short ADR per real decision, including the four above.
  • CHANGELOG.md carries the milestone story.
  • Keep dmap2's habit of writing down why a tradeoff was made — it is what made this review possible.
