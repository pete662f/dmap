Executive summary

dmap2 set out to prove that a fully self-hosted, Denmark-first consumer map app is buildable by one person on a laptop, and it proved exactly that. Vector tiles, style, glyphs, sprites, place search, reverse geocoding and orthophoto imagery all run locally with no third-party map key anywhere in the client. The service boundaries the project chose up front — SearchService, RoutingService, MapStyleLoader, OrtofotoLayerController — held up when real implementations landed behind them. That is the headline result: the seams were right.

The cost was concentrated in three places, and all three are structural rather than cosmetic. First, POI identity is reverse-engineered from pixels: because the vector tiles carry no stable place id the app has to re-derive "what did the user tap" from rendered symbol geometry, which spawned a 548-line hit detector, 790 lines of tests for it, and a whole second tile pipeline (tippecanoe, 81 MB of extra MBTiles) whose only job is to provide invisible hit-boxes. Second, Photon is the heaviest component by a wide margin and it fought back: JVM tuning, an 885 MB index, and an 85-line script that copies that index into a Docker volume with ownership markers because bind-mounting it was not reliable. Third, backend configuration is compile-time, which turned a one-line question — which host am I pointed at? — into a four-level precedence chain, two verification scripts, and a troubleshooting section in two separate docs.

Nothing here argues for a different platform or a different map engine. Kotlin + Compose + MapLibre Native + Planetiler + OSM Liberty is the right spine and should be carried forward essentially intact. The rebuild should keep the seams, keep the deterministic style patch discipline, keep the dependency-free imagery proxy, and then attack the three structural costs directly: put stable ids in the tiles, treat search as swappable data rather than a pinned service, and make the backend a runtime setting.

The one-sentence carry-forward

Keep the architecture, replace the plumbing: the app's service boundaries were correct and cheap, but every place where the app had to infer something the data should have told it directly became the most expensive code in the repository.

What worked — carry it forward unchanged

W1

Service seams declared before implementations existed

SearchService and RoutingService were interfaces with stubs from M0. When Photon landed in M2, the entire UI layer was untouched: PhotonSearchService dropped in behind the same contract, and UnavailableSearchService covers the not-configured case without a single null check in the ViewModel.

android/app/src/main/java/com/dmap/services/search/SearchService.kt — 16 lines
…/UnavailableSearchService.kt — 21 lines · …/StubRoutingService.kt — 8 lines
Carry forward: declare every backend as an interface + explicit unavailable implementation on day one, even for milestones you have not scoped yet.
W2

Patch the upstream style, never fork it

style.json is generated: clone a pinned OSM Liberty commit, rewrite it for self-hosting, then apply patch-mobile-style.py. Nobody hand-edits generated output, so the mobile cartography is reviewable as a diff of intent rather than a diff of 4,000 lines of JSON.

infra/scripts/prepare-style-assets.sh + patch-mobile-style.py (254 lines)
covered by infra/scripts/test_patch_mobile_style.py (103 lines)
Carry forward: the pattern and its test. See F5 for the one change needed.
W3

Credentials terminate at a tiny proxy, never in the client

The Dataforsyningen token exists only inside ortofoto-proxy. Android calls an unauthenticated /ortofoto/tiles/{z}/{x}/{y}.jpg. Missing token degrades to HTTP 503 instead of blocking backend startup, and the container is read_only with a 256 MB limit. Zero npm dependencies means zero supply-chain surface and no lockfile churn.

infra/services/ortofoto-proxy/server.js — ~250 lines, 0 deps, node --test coverage
Carry forward: make this the template for every third-party upstream. One tiny gateway per upstream, dependency-free, health endpoint, degrade-don't-crash.
W4

Bootstrap is incremental and honest about it

Marker files record the hashes of the scripts themselves alongside pinned upstream refs, so changing the style patch invalidates the style output but not the 40-minute Planetiler run. Repeat bootstraps are near-instant, and FORCE_REBUILD / REFRESH give explicit escape hatches.

prepare-style-assets.sh → .asset-version · bootstrap-photon.sh → .dataset-version
Carry forward: the idea (hash the recipe, not just the inputs). See F6 for the delivery mechanism.
W5

Tests were written where the logic is actually hard

790 of 1,845 test lines target the POI hit detector, and 503 target coordinate selection. That ratio is not accidental — it maps precisely onto the parts of the app that are pure decision logic. Meanwhile RenderedPoiHitDetector was deliberately structured so the MapLibre-dependent shell is thin and the ranking logic is injectable via lambdas, which is why it is testable on the JVM at all.

Carry forward: keep pushing decisions out of the SDK-facing shell into pure functions with lambda seams.
W6

Documented tradeoffs, not just documented commands

docs/setup.md explains why Planetiler replaced the OpenMapTiles PostGIS quickstart, why glyphs are downloaded rather than built, and why the Ortofoto proxy targets the Web Mercator WMTS endpoint. That is what let this review reconstruct intent from a cold start.

Carry forward: a "Backend tradeoffs" section per subsystem. See F9 for the one thing to change about doc structure.

What hurt — fix it in the rebuild

F1

POI identity is reverse-engineered from rendered pixels

Highest cost

Tapping a POI does not look anything up. It queries rendered features across four style layers in priority order, parses loose class/subclass/name properties, scores candidates by squared screen distance, then runs a second query against an invisible fill layer to guess which polygon the point belongs to — matching on normalised title, then on class, with a six-key comparator and a hard-coded list of "generic" titles to exclude. When no osm_id is present it synthesises an id by concatenating class, subclass, name and coordinates.

RenderedPoiHitDetector.kt — 548 lines
RenderedPoiHitDetectorTest.kt — 790 lines
infra/services/poi-area-tiles/ — a whole tippecanoe pipeline → denmark-poi-areas.mbtiles (81 MB)
patch-mobile-style.py — injects layer "dmap_poi_area_hitbox" at fill-opacity 0.001

Then, because the tile properties are too thin to display, every POI tap fires a reverse-geocode against Photon and merges the result back in only if it lands within 25 m — a network round-trip to recover data the tile already almost had.

Fix: put a stable osm_type:osm_id and a real category on POI features in the main Planetiler build (custom profile or a post-pass), and back it with a small local place-detail lookup. The hit detector collapses to "query one layer, read the id, fetch the record" — call it 80 lines. Delete the second tile pipeline, the invisible layer, the area-matching comparator, and the 25 m enrichment hack.
F2

Photon is the heaviest and least cooperative component

High cost

Photon needs a JVM, 2–3 GB of RAM, an 885 MB embedded index, and a slow first import from a compressed JSON dump. The repo already carries three separate mitigations for it: explicit -Xms/-Xmx plus incubator Vector API flags to stop first-query latency depending on heap growth; a switch from unpacking the prebuilt DB to importing the JSON dump because that was "more reliable with Photon 1.0.1"; and an 85-line script that copies the index into a Docker-managed volume with an ownership-marker protocol, because bind-mounting it was not good enough.

infra/scripts/sync-photon-volume.sh — 85 lines, embeds a shell script inside docker run
compose.yaml — mem_limit 3g, PHOTON_JAVA_EXTRA_FLAGS, external volume dmap2_photon_data
infra/data/search/photon — 885 MB on disk, duplicated again inside the volume

The volume is declared external: true, so Compose alone cannot start the stack — it only works through up-backend.sh. That is a hidden coupling between orchestration and a helper script.

Fix: keep the SearchService contract (it is what makes this replaceable) and re-evaluate the implementation. For a Denmark-only product, an address/POI index built directly from the OSM extract you already download — plus the official Danish address data as an optional enrichment — can be a single SQLite/FTS or Typesense-class index measured in tens of megabytes, with no JVM. Treat Photon as the fallback, not the default. If Photon stays, make the volume internal and let Compose own its lifecycle.
F3

Backend URLs are compile-time, so "which backend?" became a subsystem

High friction

Backend addresses are baked into BuildConfig through a four-level precedence chain: Gradle -P, then local.properties, then a repo-root .env parsed by ~120 lines of hand-written Kotlin DSL, then emulator defaults. Supporting that requires a script that prints the compiled URLs after every build, a second script that verifies them, and a troubleshooting paragraph — repeated in both README and setup.md — explaining that if the UI shows 10.0.2.2 you must rebuild and reinstall.

android/app/build.gradle.kts — ~120 lines of .env parsing and URL validation before the android { } block
infra/scripts/build-apk.sh (248 lines) · verify-android-build-config.sh (68 lines)
README.md + docs/setup.md — both carry the same physical-device checklist
Fix: ship build-time defaults only, and make the effective backend a runtime setting stored in DataStore, editable from a debug drawer. Switching from emulator to phone to a LAN box becomes a text field instead of a rebuild. Both verification scripts and the entire troubleshooting section disappear.
F4

Compose ↔ MapLibre is glued together with ten side effects

MapRuntimeEffects holds ten LaunchedEffect/DisposableEffect blocks that push declarative state into an imperative MapLibreMap: style loading, camera flights, marker rendering, area highlight, imagery layer, five gesture listeners, overlay auto-dismiss. Ordering between them is implicit in their keys. One of them is a while (isActive) { delay(1_500) } poll asking the location component whether it has a fix yet, because no callback was wired up.

MapRuntimeEffects.kt — 229 lines, 10 effect blocks
MapScreen.kt was 947 lines before the in-flight split into MapScreen / MapScreenUi / MapRuntimeEffects / MapViewLifecycle

The uncommitted refactor currently in the working tree does the right thing and should be treated as a finished conclusion, not work in progress: a screen file, a pure-UI file, an effects file, and a lifecycle file.

Fix: introduce an explicit MapController that owns the MapLibreMap, exposes suspend commands (flyTo, setBaseLayer, showSelection) and a Flow of map events. Compose then has one effect that collects events and one that issues commands. Replace the location poll with a real LocationEngine callback exposed as a Flow.
F5

The style patch is imperative and brittle at the seams

patch-mobile-style.py mutates upstream layers by id and raises KeyError if one is missing — which is the correct failure mode, but it means any upstream refresh is a potential hard stop, and the file is now a mix of colour tuning, zoom/rank filtering, new layer injection and layer-order surgery with explicit before-lists.

patch-mobile-style.py — 254 lines: 5 paint overrides, 3 place layers, 4 POI layers, road label + shield, 2 injected layers
Fix: split it in two — a declarative style-overrides.json (paint/layout/filter by layer id, diffable, reviewable) applied by a ~60-line generic applier, and a separate explicit step for injected layers. Add a schema check that every referenced upstream layer id still exists, run it in CI, and fail with a readable message naming the renamed layer.
F6

~1,900 lines of bash is a build system without a dependency graph

Ten shell scripts implement download, checksum, cache invalidation, Docker orchestration, artifact installation, verification and benchmarking. The incrementality is real but each script reimplements it: bootstrap-photon.sh compares an md5 marker, prepare-style-assets.sh compares a multi-field hash marker, build-poi-area-tiles.sh compares file mtimes against four dependencies. Three different mechanisms for one concept.

benchmark 206 · build-apk 248 · prepare-style-assets 222 · bootstrap-photon 193 · build-poi-area-tiles 117 · bootstrap-denmark 109 · sync-photon-volume 85 · load-env 88 · verify-android 68 · verify-backend 43 · bootstrap-common 52
Fix: declare the pipeline as a task graph (Taskfile / just / Make) with explicit sources: and generates:, so incrementality is a property of the tool. Keep the bash — it becomes the body of each task instead of the framework around it. Target: no script over ~80 lines.
F7

6.5 GB of generated artifacts live inside the working tree

infra/.cache is 4.8 GB and infra/data is 1.7 GB, both gitignored but both sitting in the repo directory. The reverted world-basemap experiment left world-lowres.mbtiles and two .cache/world-* directories behind that nothing references any more — the revert cleaned the source tree but could not clean the artifact tree.

git show 48aa29c — revert of the world-reference basemap: −42,584 lines, one day after it merged
infra/data/tiles/world-lowres.mbtiles (1.2 MB) — orphaned, no config references it
Fix: put every generated artifact under a single root outside the repo (~/.cache/dmap/ or a sibling dmap-artifacts/) resolved from one variable. The repo becomes small enough to clone, clean and reason about, and a revert cannot strand gigabytes.
F8

Nothing is enforced — no CI, no lint gate, no release path

There is no .github/ directory. Unit tests exist and are good but run only when someone remembers. Nothing checks formatting, Android Lint, or that the style patch still applies to upstream. On the release side, isMinifyEnabled = false, there is no signing config, and versionCode is pinned at 1.

android/app/build.gradle.kts — release { isMinifyEnabled = false }, versionCode = 1, no signingConfig
no gradle/libs.versions.toml — every dependency version is a hardcoded string
Fix: CI from the first commit, gated on the cheap things only: unit tests, ktlint/detekt, Android Lint, the style-patch schema check, and node --test for the proxies. None of that needs the 6.5 GB dataset. Add a version catalog and a real release build config before the first APK you hand to anyone.
F9

Security defaults point the wrong way in two places

android:usesCleartextTraffic="true" is set application-wide, for all build types, so a release build silently permits plaintext HTTP everywhere. Separately, the docs correctly recommend keeping the Dataforsyningen token in a file outside the repo tree — but the default and the actually-present configuration is DMAP_ORTHOFOTO_TOKEN in the repo-root .env. The safe path is documented; the convenient path is the unsafe one.

AndroidManifest.xml — usesCleartextTraffic="true" on <application>
.env — DMAP_ORTHOFOTO_TOKEN set inline, despite README recommending DMAP_ORTHOFOTO_TOKEN_FILE
Fix: cleartext allowed only in the debug manifest, scoped by a network security config to private address ranges; release is HTTPS-only. Make the token file the default and only path, and have the proxy refuse to start with an inline token unless an explicit dev flag is set.
F10

Docs narrate milestones, so they age instead of accumulating

README, setup.md and architecture.md are all written as "what M2 includes / what M1 intentionally does not". The content is high quality, but a reader in M4 has to mentally date every sentence, and statements like "M1 intentionally downloads fonts" describe a decision that is simply true now.

Fix: split into timeless reference (architecture, setup, contracts, tradeoffs — always describing the current state) and a dated CHANGELOG/decision log that carries the milestone narrative and the ADRs.

Complexity hot spots

Where the lines actually are, and what each cluster is really doing:

Photon plumbing 3320 bootstrap-photon + sync-photon-volume + container entrypoint (F2)

Two clusters — POI tap resolution and Photon plumbing — together account for roughly a third of the non-UI code in the project, and both exist to compensate for data that was not shaped right upstream. That is the single most transferable observation in this review.

The ten learnings

  1. Shape the data so the client never has to infer. Stable ids in the tiles would have deleted ~1,400 lines and a whole tile pipeline.
  2. Declare service interfaces before you have services. It cost 45 lines total and made Photon a drop-in.
  3. Environment selection belongs at runtime, not at compile time. Compile-time backends produced two scripts, 120 lines of Gradle, and a recurring support question.
  4. Generated artifacts live outside the repo. 6.5 GB inside the tree makes reverts, clones and cleanups all worse.
  5. Give the imperative SDK an explicit owner. Ten synchronising effects is the signal that a controller object is missing.
  6. Patch upstream, don't fork it — but keep the patch declarative and schema-checked in CI.
  7. Prefer boring, dependency-free gateways for third-party upstreams. The 0-dependency Node proxy has caused zero problems.
  8. Weigh runtime cost before adopting a backend. Photon's 885 MB / 3 GB RAM / JVM profile drove three separate workarounds; the contract around it is what saved the design.
  9. Enforce quality with CI from commit one, gated only on things that run without the dataset.
  10. Make the safe configuration the default configuration. Documented-safe plus convenient-unsafe means the unsafe path is what actually gets used.
